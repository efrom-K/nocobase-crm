# Выкладка и правки через GitHub

```
правка кода → git push (main) ──► GitHub Actions: проверки (CI)
                                        │ зелёные
сервер (cron, раз в минуту) ◄──────────┘ смотрит статус коммита в GitHub API
        │ git fetch → deploy → запись блоков в NocoBase (таблица flowModels)
        └► сообщение в колокольчик «Выкладка CRM: обновлено» + строка в deploy.log
```

Почему так: репозиторий публичный, а сервер стоит в закрытой сети. Поэтому **CI работает на серверах GitHub, а выкладка «на вытягивание»
запускается с самого сервера** (только исходящее соединение, без секретов, без открытых портов и без self-hosted runner: чужой pull request не сможет
выполнить код в вашей сети).

## Что проверяет CI (`scripts/ci_checks.py`, его же можно запустить локально)
- синтаксис каждого блока `src/*.js` в той форме, в какой его исполняет NocoBase, и запрет функций, которых нет в песочнице (`MutationObserver`, `requestAnimationFrame`, `URLSearchParams`, `FormData`): блок с ними падает целиком;
- Python-скрипты компилируются, все JSON валидны, `deploy/blocks.json` ссылается на существующие файлы;
- **личные данные и секреты**: внутренние IP, e-mail не из белого списка, токены/ключи/пароли, данные в `db/schema.sql`, запрещённые файлы (`.env`, ключи, дампы).
  Свои «запретные слова» (названия объектов, фамилии, домен) можно положить в секрет репозитория `CI_DENYLIST_REGEX` (Settings → Secrets and variables → Actions):
  это регулярное выражение, оно нигде не публикуется и проверяется по всем файлам.

## Что выкладывается автоматически
Только код JS-блоков (`deploy/blocks.json`: uid блока → файл). Остальное осознанно делается руками:
структура страницы (`db/registry-page.*.json`), миграции БД (`db/migrations/`), переводы плагинов (`scripts/ru/`), настройка каналов уведомлений.

## Обычная работа
1. Правим файл в `src/`, коммит, `git push` в `main` (или через pull request — CI запустится и там).
2. Через 1–2 минуты страницы CRM получают новый код (обновить страницу в браузере). Результат — в колокольчике администратора и в `~/nb_deploy/deploy.log`.
3. Если CI красный, на сервер ничего не попадёт, в колокольчик придёт «проверки не прошли».

## Команды на сервере (`~/nb_deploy/nb_deploy.py`)

### Первичная установка справочника объектов (миграция 005)

До выкладки интерфейса объектов: сделать полный резервный дамп БД, затем запустить `scripts/setup_object_directory.py` из проверенного коммита. Без аргументов он только показывает число договоров без объекта и без записи справочника. С `--apply` выполняет транзакционную миграцию, регистрирует `object_id` в NocoBase и добавляет ролям отделов создание **только названия** объекта; существующие права и назначения управляющих не заменяет. Нужны `NB_SSH`, `NB_URL`, `NB_TOKEN` (для локального Docker `NB_SSH` не задавать). Секреты передавать окружением, не коммитить.

Миграция добавляет отсутствующие названия из договоров, но не угадывает пустые. Неоднозначные дубли и пустые объекты опубликованных договоров прерывают транзакцию. Объекты не переименовываются, договоры не удаляются. Переносы между разделами продолжают передавать название — триггер восстанавливает тот же ID. Имя объекта по-прежнему используется другими модулями; отдельный интерфейс переименования в эту правку не входит.

Настройка полей/прав идёт после SQL, отдельными API-запросами: при сбое исправить причину и повторить `--apply` до выкладки интерфейса. Уже установленные поля/разрешения пропускаются. Затем обычный PR → CI → main → агент. Проверить создание через «＋», выбор в договоре, отсутствие дублей, счётчики и сохранность прежних договоров. В CI миграция проверяется на изолированной схеме PostgreSQL с ROLLBACK.

### Команды агента

| Команда | Что делает |
|---|---|
| `status` | сравнить репозиторий и живой NocoBase по каждому блоку |
| `deploy [--force]` | выложить сразу из рабочей копии (`--force` — поверх ручных правок) |
| `rollback` | вернуть блоки из резервной копии и заморозить автовыкладку до нового коммита |
| `export --to DIR` | сохранить живой код блоков в файлы, если что-то правили прямо в интерфейсе NocoBase |

Резервная копия предыдущего кода делается перед каждой выкладкой (`~/nb_deploy/backups/`).

**Ручные правки в интерфейсе.** Если блок изменили прямо в NocoBase, агент это замечает (живой код не совпадает ни с репозиторием, ни с прошлой выкладкой)
и такой блок **не перезаписывает**, а сообщает об этом. Дальше: `export`, закоммитить, либо `deploy --force`.

## Установка агента на сервер (один раз)
```bash
mkdir -p ~/nb_deploy && cd ~/nb_deploy
git clone https://github.com/<владелец>/nocobase-crm repo
cp repo/deploy/nb_deploy.py .                    # агент ставится копированием и из репозитория сам не обновляется
NB_NOTIFY_USER_IDS=2 python3 nb_deploy.py init   # считаем текущее состояние «уже выложено»
( crontab -l; echo '* * * * * NB_NOTIFY_USER_IDS=2 flock -n /tmp/nb_deploy.lock python3 ~/nb_deploy/nb_deploy.py auto >> ~/nb_deploy/deploy.log 2>&1' ) | crontab -
```
Нужны: git, python3, `sudo docker` без пароля (для доступа к контейнеру PostgreSQL), исходящий доступ к github.com и api.github.com.
Запуск с ноутбука: `NB_SSH=user@server python3 deploy/nb_deploy.py status`.

## Безопасность
- Выкладка идёт только из ветки `main` и только для коммитов с успешным CI; `main` может менять только владелец репозитория (форк-PR ничего не выкладывают).
- Агент не исполняет код из репозитория, он лишь читает JS-файлы и записывает их в NocoBase как данные. Но JS-блок исполняется в браузерах сотрудников, поэтому доступ к `main` = доступ к CRM:
  включите двухфакторную аутентификацию на GitHub и, по желанию, защиту ветки (Settings → Branches → Require status checks).
- Обновление самого `nb_deploy.py` — осознанное, копированием.
